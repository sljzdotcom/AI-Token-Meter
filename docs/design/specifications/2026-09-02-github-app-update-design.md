# AI Token Meter GitHub 应用内更新设计

- **需求：** `REQ-20260902-019`
- **日期：** 2026-09-02
- **状态：** 口头规格已确认，待书面规格复核

## 目标

在 AI Token Meter 的 Settings → About 中提供明确、可控且安全的应用内更新流程。用户手动点击“检查更新”后，应用从公开 GitHub 项目的正式更新源判断是否存在比当前版本更新的 Release；发现新版时启用“立即更新”，随后完成下载、真实性校验、安装、退出旧进程和重新启动。

本功能不得后台轮询、不得静默安装、不得信任未签名的可执行文件，也不得把任何更新私钥或 GitHub 凭证写入源码、日志、分发包或公开仓库。

## 已确认的交互策略

采用**方案 A：手动检查 + 一键更新**。

- 应用启动时不自动联网检查；
- 不定时后台检查；
- 用户点击“检查更新”才发起检查；
- 发现新版后，“立即更新”变为可用；
- 用户点击“立即更新”后进入下载、校验、安装和重启流程；
- 不提供静默安装开关，也不在退出应用时偷偷安装。

## 技术方案与取舍

采用 Sparkle 2 作为更新执行引擎，并使用 GitHub 承载应用更新清单和 Release ZIP。

选择 Sparkle 的原因：

- 它专门处理正在运行的 macOS App 自替换、权限提升、原子安装和重启；
- 内置 EdDSA 更新包签名验证，能够拒绝被替换或损坏的 ZIP；
- 对只读位置、App Translocation、下载失败和安装失败具有成熟的错误路径；
- SwiftUI 可以通过程序化 API 发起用户主动检查；
- 避免维护一个高风险的自制 shell/helper 更新器。

不采用以下方案：

1. **自制 GitHub Releases 更新器：** 需要自行正确实现锁、权限、隔离属性、进程退出、回滚、签名校验与重启，风险与维护成本过高；
2. **只打开 GitHub 下载页：** 无法满足自动下载和安装；
3. **后台或静默更新：** 不符合已确认的方案 A，也会引入未经用户触发的网络访问和安装行为。

Sparkle 依赖在 `Package.swift` 中固定到实施时确认的稳定 2.x 版本，不跟踪分支或浮动版本。构建产物必须完整嵌入 `Sparkle.framework` 及其随附 helper/XPC 内容，不能只复制主动态库。

## Settings 界面

更新入口位于现有 About 标签页，放在应用身份卡与 Privacy 之间，使用 Settings 固定系统字体。

“Software Update”区包含：

- 当前版本，例如 `Version 0.2.0 (4)`；
- 状态文字；
- 最近一次成功或失败检查的本地时间；
- “检查更新”按钮；
- “立即更新”按钮。

状态采用以下有限集合：

- `尚未检查更新`；
- `正在检查…`；
- `当前已是最新版本`；
- `发现新版本 0.2.1`；
- `正在下载…`，尽可能显示百分比；
- `正在验证更新…`；
- `准备安装并重新启动…`；
- 可读的失败说明。

按钮规则：

- 检查进行中或更新安装进行中时禁用“检查更新”，防止并发任务；
- 尚未发现新版时禁用“立即更新”；
- 发现可安装新版后启用“立即更新”；
- 更新开始后禁用两个按钮；
- 失败后恢复“检查更新”，现有应用继续可用；
- 无更新时不显示虚假的 0% 下载进度。

发现更新时显示版本号、发布日期和经过纯文本处理的简短 Release Notes。第一版不在 Settings 中嵌入网页、不执行 Release Notes 中的 HTML 或脚本。

## 更新状态与组件边界

新增一个主线程隔离的 `UpdateCoordinator` 作为 Settings 和 Sparkle 之间的唯一桥梁：

- 启动并持有单个 Sparkle updater 实例；
- 暴露当前版本、可否检查、可用版本、检查时间、进度与错误状态；
- 接收 Settings 的“检查更新”和“立即更新”动作；
- 将 Sparkle delegate/user-driver 回调归一化为可测试的应用状态；
- 不读取 Provider 凭证，也不进入现有用量刷新循环。

检查阶段使用 Sparkle 的信息检查能力获得有效更新项，不自动下载。安装阶段由用户点击“立即更新”后交给 Sparkle 标准安装链路处理。若 Sparkle 的稳定公开 API 不允许在完全保持标准安全流程的前提下把“发现”和“安装”拆成两个独立动作，则保留 Settings 中的两个按钮，但“立即更新”负责把已经发现的更新带入 Sparkle 标准确认/安装界面；不调用私有 API，也不自行绕过 Sparkle 的用户授权步骤。

应用生命周期只负责创建一个共享 coordinator，并传入 About 页面。更新状态不写入 Provider 快照，不影响浮动条、详情页或 Widget。

## GitHub 更新源

更新源使用公开仓库中的稳定 HTTPS appcast：

`https://raw.githubusercontent.com/sljzdotcom/AI-Token-Meter/main/appcast.xml`

appcast 只列出正式、可公开下载的稳定 Release：

- 排除 Draft；
- 排除 Pre-release；
- 每个条目指向对应 GitHub Release 的 Apple Silicon ZIP；
- 包含短版本号、递增 build、发布日期、最低 macOS 版本、文件长度、下载 URL 和 EdDSA 签名；
- 版本判断以 Sparkle 支持的规范比较器和递增 `CFBundleVersion` 为准；
- 同一 build 不重复安装，低版本不作为普通更新下发。

`SUFeedURL` 和 `SUPublicEDKey` 写入应用 `Info.plist`。自动检查与自动下载默认显式关闭，防止 Sparkle 首次启动询问后台检查权限。

GitHub API 不作为安装真实性的信任根。即使 GitHub 元数据或下载链路被错误替换，未通过内置公钥验证的更新包也必须被拒绝。

## 密钥与供应链安全

生成一对专用于 AI Token Meter 更新的 Ed25519/EdDSA 密钥：

- **公钥**嵌入 App 的 `Info.plist`，可以公开；
- **私钥**只保存在发布者本机 Keychain；如果未来启用自动 Release，再以 GitHub Actions Secret 保存；
- 私钥不得出现在 Git、shell 历史、构建日志、测试 fixture、截图或 Release 资产中；
- 测试使用独立测试密钥，绝不复制生产私钥；
- 发布脚本输出签名和哈希，但不打印私钥。

Release ZIP 继续生成 SHA-256 供用户人工核验，同时增加 Sparkle EdDSA 签名用于应用自动验证。SHA-256 文件本身不是更新真实性证明，不能替代 EdDSA。

当前项目使用 ad-hoc 签名且未经过 Apple Developer ID 公证。第一版更新器仍可依靠 Sparkle EdDSA 保护更新包，但文档必须继续明确 Gatekeeper 限制；取得 Developer ID 后，Release 应升级为 Developer ID 签名和公证，并复验 Sparkle helper 的签名嵌套关系。

## 构建与发布流程

更新功能进入首个版本时，版本升级到 `0.2.0`、build `4`。原因是从 `0.1.2` 的只读监控工具新增了应用安装能力，属于明显的新功能边界。

发布流程扩展为：

1. 更新版本、Changelog 和文档；
2. 完整运行测试与公开发布安全扫描；
3. 构建 arm64 Release App，完整嵌入 Sparkle；
4. 验证主 App、Sparkle framework/helper、资源包和最终签名；
5. 生成版本 ZIP 与 SHA-256；
6. 使用生产更新私钥为 ZIP 生成 EdDSA 签名；
7. 创建不可变 Git tag 与 GitHub Release；
8. 更新并验证 `appcast.xml`；
9. 提交 appcast 并等待公开 CI 通过；
10. 从匿名网络重新下载 feed 和 ZIP，复验 URL、长度、SHA-256、EdDSA 和解压启动。

发布脚本必须在缺失更新私钥、版本/build 未递增、Git 工作树不符合规则、测试失败、签名失败或同名 Release 资产不一致时立即停止，不得生成看似成功的半成品更新。

## 首次升级边界

公开的 `v0.1.2` 不包含 Sparkle 和更新公钥，因此无法通过应用内更新获得 `v0.2.0`。用户必须手动从 GitHub 安装一次 `v0.2.0`。从 `v0.2.0` 开始，后续正式版本才可以使用 Settings 内更新。

README、Release Notes 和 Settings 更新区均应明确这一点，避免用户在旧版中寻找不存在的按钮。

## 错误处理与回退

- **离线、DNS、超时或 GitHub 不可达：** 显示检查失败及可重试状态，不改变现有 App；
- **appcast 格式错误：** 拒绝更新并记录脱敏诊断；
- **Release 无兼容资产：** 视为当前没有可安装更新，不下载其他架构；
- **EdDSA 签名缺失或无效：** 硬失败，绝不提供绕过按钮；
- **ZIP 损坏或长度不符：** 删除临时下载并保留当前版本；
- **应用目录不可写：** 使用 Sparkle 的标准授权路径；用户取消授权则安全退出更新流程；
- **安装或重启失败：** 保留/恢复旧版本，提供 GitHub Release 手动下载入口和可诊断错误；
- **重复点击或并发检查：** coordinator 串行化状态，不创建第二个 updater；
- **应用正在退出：** 不启动新检查或下载。

应用日志只记录版本、阶段、HTTP/框架错误类别与时间，不记录 Cookie、Authorization、GitHub 登录状态或任何私钥材料。

## 测试与验收

### 自动测试

- 当前版本与 build 的读取和显示；
- 初始、检查中、无更新、有更新、下载中、验证中、失败和安装状态；
- 两个按钮在各状态下的启用规则；
- 多次点击不会产生并发检查；
- 正式版高版本被接受，同版、低版、Draft、Pre-release 和错误架构不被安装；
- Release Notes 纯文本化与长度限制；
- 断网、超时、无效 XML、资源缺失和签名失败；
- 生产构建 `Info.plist` 包含正确 feed URL、公钥及禁用自动检查配置；
- `Sparkle.framework` 与 helpers 完整存在并通过 bundle/签名门禁；
- 发布脚本在私钥缺失或版本未递增时失败；
- 公开发布扫描确认仓库、历史和 ZIP 不含私钥。

### 集成验收

使用独立测试密钥和本地 HTTPS/HTTP 测试 feed 创建旧版本夹具：

1. 旧版显示“尚未检查更新”；
2. 手动检查发现测试新版；
3. “立即更新”下载安装；
4. 应用重新启动并报告新版本/build；
5. 篡改 ZIP 后签名验证失败且旧版仍可运行；
6. 无更新和离线路径均不破坏当前安装。

最终公开候选还需执行全量 Swift 测试、文档门禁、Release 构建、资源扫描、严格签名验证、ZIP 解压验证、跨目录启动和匿名 GitHub 下载验证。

## 非目标

- 不启用后台或定时检查；
- 不启用静默下载/安装；
- 不支持 Intel/x86_64 Release；
- 不恢复当前延期的 Widget 证书事项；
- 不购买 Apple Developer 会员，也不在本需求中宣称完成 Developer ID 公证；
- 不建立自制更新协议或自制特权 helper；
- 不让用户在 Settings 中切换任意 feed URL、降级版本或绕过签名验证。

## 自检结论

- **需求覆盖：** 两个指定按钮、GitHub 新版本发现、自动下载、校验、安装与重启均有明确路径；
- **用户控制：** 符合已确认的方案 A，没有后台联网或静默安装；
- **安全边界：** 更新真实性由嵌入公钥验证，生产私钥不进入仓库；
- **失败安全：** 任何网络、格式、签名或安装失败都保留当前可运行版本；
- **现状诚实：** 明确记录 ad-hoc/Gatekeeper 限制和 `v0.1.2 → v0.2.0` 必须手动升级；
- **可测试性：** 状态模型、构建门禁、测试 feed、篡改包和公开发布均可验证；
- **范围控制：** 不顺带引入后台更新、Intel 包、Widget 或 Developer ID 项目。
