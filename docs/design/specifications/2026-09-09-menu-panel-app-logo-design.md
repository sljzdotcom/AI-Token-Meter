# 菜单面板应用 Logo 展示

关联 `REQ-20260909-002`。用户要求在菜单弹出面板顶部的 “AI Token Meter” 名称旁加入现有应用 Logo，并与当前背景自然融合。协调入口已确认普通尺寸与留白按推荐方案执行，重大视觉变化才需要再次选择；本规格不引入新的视觉方向。

## 当前问题

macOS 的窗口式 `MenuBarExtra` 由 `MenuBarPanel` 提供。顶部目前只有产品名、副标题和右侧刷新按钮，缺少与应用图标的品牌联系。Windows 使用原生托盘菜单，对应菜单直接从四个 Provider 摘要开始；Settings 顶部已有 Logo，但它不属于托盘菜单，不能作为本需求的完成证据。

## 方案比较与决定

1. **原生小图标品牌行（采用）：** macOS 在标题/副标题左侧放 32pt 现有应用图标；Windows 在托盘菜单第一行放由系统缩放的现有应用图标与产品名，品牌行不可点击。它复用已打包图标，不增加资产，且保持两个平台各自的原生菜单样式。
2. **只在标题文字内部放 16–20pt 图标：** 占用更少，但图标会低于双行标题块的视觉分量，也更容易与标题基线挤在一起。
3. **为图标增加独立底板、描边或阴影：** 品牌识别更强，但会在现有菜单背景上形成新的视觉层级，与用户要求的自然融合相冲突。

## macOS 设计

- `MenuBarPanel` 继续保持 380pt 宽、16pt 外边距和现有垂直间距。
- 顶部改为：32×32pt 应用图标、10pt 间距、原有产品名/副标题文字块、弹性空白、原有刷新按钮。
- 图标直接读取 `NSApplication.shared.applicationIconImage`，使用高质量缩放；不复制 PNG、不增加底板、边框、圆角或阴影。
- 图标是装饰元素，对辅助功能隐藏；产品名、副标题、刷新按钮的文字、语义、禁用状态和帮助提示不变。
- 为真实渲染测试允许注入合成图标；生产默认仍只使用应用自身图标。

## Windows 设计

- 原生托盘菜单顶部新增一个带图标的 `IconMenuItem`，文本固定为产品名 “AI Token Meter”，并设为不可点击。
- 图标复用 `AppHandle.default_window_icon()`，由 Windows 原生菜单缩放；该行之后增加分隔线，再接原有四个 Provider 摘要和操作项。
- 产品名不随中文界面翻译；Provider 摘要、操作本地化、事件路由、托盘图标与现有菜单更新监听保持不变。
- Settings 已有的 Logo 保持原样，不能用它替代托盘菜单验收。

## 测试与验收

- macOS 先渲染未修改的真实 `MenuBarPanel`，以注入的高对比合成图标断言顶部左侧应出现 32pt 图像；旧实现因不接受/不显示该图标而失败。最小实现后重跑，并保留现有字体、菜单栏标签和按钮回归。
- Windows 以 Tauri MockRuntime 构建真实品牌菜单项，断言它是带固定 ID 的不可点击图标菜单项、文本正确，并用非法 RGBA 图像确认构建确实消费图标数据；旧实现因缺少构建入口而失败。原生 Windows CI 继续负责编译和安装器级复验。
- 完成后运行 Swift 定向与全量测试、Windows Rust 定向与全量测试、格式/严格 Clippy、Windows 前端与生产构建、跨平台合同、文档和公开安全检查。
- 自动渲染只使用合成颜色，不含用户额度、账号或截图元数据。真实 Windows 托盘菜单的系统主题/DPI观感仍需交互式 Windows 现场确认，不能由 macOS MockRuntime 冒充。

## 范围边界

不修改菜单背景、字体选择、Provider 卡片、刷新逻辑、Settings 布局、浮动条、详情窗口、版本号、签名或更新源。本项完成后只进行已授权的本地主分支整合；不创建新标签、Release 或自动发布下一版本。
