# Codex 超时进程取证稳定性设计

关联需求：`REQ-20260909-009`。日期：2026-09-09。

## 问题

0.6.3 首次正式打包在创建标签和 GitHub Release 前被完整 Swift 门禁拦截。`CLICollectorTests.codexTimeoutIsBounded` 已得到预期的 `timedOut`，但随后等待子进程写入临时 PID 文件时抛出 `transportFailure`。相同失败形态在既往发布记录中出现过。

旧测试把两个条件绑定在一起：父进程必须在 0.5 秒内终止忽略普通终止信号的子进程；子进程还必须先获得调度并运行 shell 夹具，把自己的 PID 写入文件。完整测试负载下，父进程可以在后一个动作发生前正确超时并回收子进程，使测试把正确行为误报为失败。

## 方案

`CodexAppServerClient` 在 `Process.run()` 成功且进程已经登记到清理容器后，调用一个默认为空的内部启动观察闭包，并传出 `Process.processIdentifier`。生产调用不提供闭包，执行路径和超时期限不变。

超时测试使用带锁的内存捕获器接收该 PID，不再要求被测子进程写文件。测试继续要求：

- 请求得到 `UsageCollectionError.timedOut`；
- 总耗时小于 2 秒，产品请求期限仍为 0.5 秒；
- 记录到真实子进程 PID；
- 该进程在 2 秒内退出。

观察闭包放在进程登记之后。即使截止信号与启动相邻发生，清理容器也已持有进程和管道，可以执行既有终止与回收流程。闭包不抛错、不改变返回值，也不延长生产默认路径。

## 未改变的边界

- 不改变 Codex app-server 命令、协议、环境、认证、输出解析或公开 API。
- 不改变 0.5 秒测试请求期限、2 秒总耗时和真实进程退出断言。
- 另一个覆盖“超时先于进程登记”的测试继续使用受控门闩和 PID 文件，因为它验证的是不同的登记竞态，夹具会先获得运行机会。
- 发布仍须重新通过完整 Swift 门禁、macOS Release App、PR 与合并后双平台 CI；不能用单次重跑替代修复证据。

## 验收

先让改写后的测试因缺少启动观察入口产生编译失败，再实现最小入口使该用例和全部 `CLICollectorTests` 转绿。随后在正式发布脚本使用的完整测试编排中复验，并完成文档、差异、构建、审查及原生 CI。
