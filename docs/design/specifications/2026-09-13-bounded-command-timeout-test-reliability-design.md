# BoundedCommandRunner停止测试可靠性设计

关联需求：`REQ-20260913-004`、`REQ-20260912-006`。日期：2026-09-13。

## 问题与证据边界

v0.9.1发布证据PR的macOS CI仅`terminatesAfterTheConfiguredDeadline`失败：调用正确返回`UsageCollectionError.timedOut`，但从调用前开始测量的完整墙钟耗时为1.507秒，超过一秒断言。相同测试在本机低负载连续20次通过。

被测请求的超时为50毫秒。旧断言把超时任务获得调度前的等待、进程启动、超时等待、终止、退出通知与输出EOF排空全部计入一秒。原CI日志只能证明`timedOut`已经返回和完整耗时为1.507秒，无法区分延迟发生在超时触发之前还是停止后的清理期间，因此旧断言既可能受共享runner调度影响，也不能给出清理超限的准确证据。已有取消测试已将同类门限起点移到真实取消请求时刻。

## 方案

`BoundedCommandRunner`增加一个默认为空的内部超时观察闭包，只在50毫秒睡眠完成后、提交`timedOut`停止请求前调用。测试使用单调时钟记录该事件，并分别断言：

- 超时事件没有早于配置的50毫秒发生；
- 调用返回`UsageCollectionError.timedOut`；
- 从真实超时停止请求到完成进程清理并返回少于一秒。

夹具改用30秒子进程，确保即使超时任务明显延迟，终止失效也不能靠子进程自然退出而误通过。审查变异验证曾在延迟触发并禁用停止操作时让原2秒夹具约2.006秒后通过，证明长寿命夹具是必要条件。

公开初始化器仍创建无观察者的runner。观察闭包不改变停止原因、信号、强制终止期限、输出排空或返回值。

PR #44后续CI又显示取消调用在正确返回`CancellationError`后完整墙钟为1.105秒。runner本身允许0.5秒强制终止后备与最多0.5秒EOF排空，而测试任务在操作系统进程退出后仍需获得调度才能返回；因此返回墙钟不能准确证明子进程是否在取消后一秒内完成清理。

runner再增加默认关闭的内部进程退出观察闭包，直接接到既有`ProcessTerminationWaiter`只执行一次的退出事件。超时与取消测试均从对应停止请求计时到操作系统进程退出，同时继续分别等待并断言`timedOut`与`CancellationError`。30秒子进程确保退出事件只能来自停止流程；异步调用最终返回仍是独立的必需断言。

## 验收

两轮测试分别调用尚不存在的超时和进程退出观察初始化器，均保留准确编译失败证据。实现最小入口后运行四项连续回归、完整Swift门禁、文档和公开安全检查。候选经独立审查与PR双平台CI通过后合入main。
