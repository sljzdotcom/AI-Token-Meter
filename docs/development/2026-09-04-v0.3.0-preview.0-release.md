# v0.3.0-preview.0 双平台发布记录

## 背景与目标

`0.2.2` 只公开了 macOS Apple Silicon 资产。Windows 11 x64 客户端及稳定显示器位置修复已经合入 `main` 并通过双平台 CI，因此本阶段将它们交付为首个 macOS/Windows 同版本 Preview。

对应需求：`REQ-20260903-011`。发布版本为 `0.3.0-preview.0`，macOS build 为 `7`。

## 发布范围

- 同步根 `VERSION`、macOS Info.plist、Windows npm、Cargo 与 Tauri 元数据；
- 把 `CHANGELOG.md` 的既有 `Unreleased` 内容固化为本版本；
- 生成 macOS arm64 ZIP、SHA-256 与 Preview appcast；
- 在 Windows GitHub runner 构建同时用于安装与更新的 current-user NSIS、配套 minisign `.exe.sig` 与 SHA-256；
- 同一 Git tag 和 GitHub Release 发布两平台资产；
- 稳定 macOS appcast 不指向 prerelease，Windows Preview 使用独立固定 feed。

## Windows 首次更新签名身份

仓库在本版本前只有 Tauri updater 公钥，没有可供 GitHub Actions 使用的私钥 Secret。由于此前没有公开 Windows Release，本阶段可以安全建立首个 Windows 信任根：

- 使用 Tauri 官方 CLI 生成新的密码保护 minisign keypair；
- 私钥与密码仅写入 GitHub Actions Secret，不写入 Git、Artifact、Release 或日志；
- 仓库只更新公开验证密钥；
- 临时本机密钥在 Secret 写入和远端构建验证完成后立即删除；
- 后续 Windows Preview 必须沿用该信任根；如私钥疑似泄露，按发布流程执行轮换与手动恢复，不能静默替换。

用户于 2026-09-04 明确授权配置两个 GitHub Actions Secret。写入后只核对到 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 两个名称，未读取或输出其内容；本机临时私钥、公钥副本、密码和生成日志随后全部删除，临时目录也已移除。

## 自动化验证

本地发布候选准备证据：

- macOS：374 项主测试与 12 项独立 PTY 测试通过；
- Windows：14 项 frontend 测试、production build、严格 rustfmt/Clippy 和 122 项 Rust 测试通过；其中需要本机 loopback 的 DeepSeek 测试在允许本地监听的隔离外测试环境重跑通过；
- 版本同步、135 份 Markdown、Release feed probe 和公开秘密扫描通过；
- macOS Sparkle 与 Windows minisign：正式 Release workflow 与公开重下副本均验证通过；
- GitHub Release 两平台资产已从公开 URL 重新下载，两份 SHA-256 均通过。

首次 Release workflow `33813010911` 的 macOS 门禁以及 Windows frontend、严格 Clippy 和 122 项 Rust 测试均通过，但在签名构建前被跨平台合同检查器安全阻断。根因不是发布入口缺少 Git 可执行位：该文件在索引中为 `100755`；而是检查器使用 `Pathname#executable?`，该宿主文件系统权限查询在 Windows runner 上不能表达 Git 可执行位。修复后检查器直接核对 Git 索引模式，并增加真实临时 Git 仓库回归，覆盖“Git 可执行/工作区不可执行”和“Git 不可执行/工作区可执行”两个相反场景。

第二次 Release workflow `33814393456` 已证明上述 Windows 可执行位修复有效，并完成 frontend、严格 Clippy、122 项 Rust 测试以及 Tauri 签名 NSIS 构建。Runner 的实际输出为 `AI Token Meter_0.3.0-preview.0_x64-setup.exe` 与紧邻的 `.exe.sig`；旧流程错误假设 Tauri 会额外生成 `.nsis.zip`，因此在资产标准化阶段中止。修复后用跨平台 Node 脚本要求恰好一个非空 `setup.exe` 及同名非空签名，统一重命名、计算 SHA-256，并让签名验证、Release 资产和 `latest.json` 全部指向同一个 NSIS 安装器。回归同时覆盖重复安装器与缺失签名必须失败。

## 本机与界面验收

本阶段可验证 macOS Release 构建、资源、签名结构和公开下载。Windows 交互式视觉/DPI/拖动/全屏/真实账户验收需要 Windows 11 x64 用户会话，继续保留在 `REQ-20260903-004` 与 `REQ-20260901-004`，不得由 CI 安装器替代。

第三次 Release workflow `33816010376` 在提交 `704342e` 上完成全链路：macOS 门禁通过；Windows frontend、严格 Clippy、122 项 Rust、版本合同、签名 NSIS 构建、标准化、SHA-256、内嵌公钥 minisign 验证与 Artifact 上传通过；publish job 验证资产、生成 `latest.json`、公开 prerelease，并把相同 manifest 发布到固定 `windows-preview-feed`。稳定 macOS `appcast.xml` 没有被 Preview 改写，首项仍为 `0.2.2`。

公开后使用不带 GitHub CLI 凭证的公网 URL 重新下载全部七个 Release 资产和固定 Preview manifest。macOS ZIP 通过 SHA-256 与 Sparkle EdDSA 验证，人工追加内容的临时副本被拒绝；Windows PE/NSIS 安装器通过 SHA-256 与应用内置 Tauri 公钥验证；`latest.json` 与 `latest-preview.json` 字节一致，版本为 `0.3.0-preview.0`，下载 URL 指向同一签名 `setup.exe`。

## 已知限制与后续工作

- Windows 安装器没有 Authenticode，SmartScreen 可能显示 unknown publisher；
- `preview.0` 只能作为 Windows 签名升级演练起点，必须由后续 `preview.1` 验证原位升级与错误签名拒绝；
- macOS Widget 和 Windows 真机交互仍按现有延期/环境限制事项管理。
- GitHub Actions 当前提示 `actions/upload-artifact@v4` 与 `actions/download-artifact@v5` 的 Node 20 运行时将弃用；Runner 本次已强制使用 Node 24 且发布成功，后续在对应 Action 发布兼容版本时升级，不影响本版本资产。
