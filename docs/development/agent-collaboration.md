# 需求对话与开发对话协作

关联需求：REQ-20260908-008。建立日期：2026-09-08。

## 分工

用户继续在原对话提交需求、截图、缺陷和验收反馈，不必在两个对话之间复制信息。原对话是协调入口，开发对话是同一项目下的长期执行入口；这是两个可互相发消息的 Codex 对话，不依赖仅存于单轮的临时子代理。

协调入口负责：先更新[唯一需求台账](../requirements-backlog.md)，确定优先级和验收口径，提交需求记录，将任务和基线交给开发对话，核对成果，再向用户汇报或请求必要决定。

开发入口负责：读取项目规则、台账、当前状态与指定规格，在隔离工作区实现、测试、自审/独立审查和补文档，按需求授权交付代码。不自动扩大范围、消费凭证/重置券或发布。

## 派工与回传

1. 协调入口先检查开发对话是否已有工作。新想法只登记；除非用户改变优先级，不打断当前工作。
2. 派工包含需求 ID、目标、限制、验收口径、需求/规格提交 SHA、主仓库路径和协调对话的回传 ID。对话 ID 只放在工具消息中，不写入公开产品文档。
3. 开发对话先核对自己的 checkout 是否包含派工基线。若为旧分支，先检查工作树与提交状态，再安全引入已提交需求；禁止覆盖其他改动或强制重置。工作区不共享未提交文件，不能假设另一窗口修改立即可见。
4. 开发过程中用同一台账记录当前事项与证据。在不同 checkout 修改台账时，只更新自己负责的行/记录；由协调入口整合提交，保留期间新增的需求，不能用旧文件整份覆盖。
5. 完成、阻塞或需要用户选择时，开发对话主动向派工指定的协调对话发送结果消息。消息注明“开发结果回传”、需求 ID、提交/分支/工作区、测试、限制、需用户确认内容和是否发布；无需用户切换窗口。
6. 协调入口收到回传后核对提交和测试，必要时做验收，再在原对话给出结论。明确区分实现、测试、合并、发布、真机验收，不凭“完成”二字推断全部完成。
7. 可执行需求结束后开发对话结束当前轮并待命，不空转轮询。下一次由协调入口发送新任务唤起；若回传未到，协调入口使用任务状态查询/等待核对，不虚构后台监控已运行。

## 权限和现状

- 普通实现决策按推荐方案继续；重大产品分歧、视觉选择或新增授权需求通过协调入口询问用户。
- 合并沿用用户既有授权，但必须通过验证；发布需遵守该项最新指示。未发布改动不代表需要马上发布。
- 建立协作时公开版本为 0.5.1；REQ-20260908-007 已实现且明确暂不发布。REQ-20260908-001 的真实 Windows/WSL 账号验收仍受环境限制，不得冒充已通过。
- 初次接入只核对基线和队列并报告就绪；没有明确可执行派工时，不重开历史受限或已延期事项。
