# 需求对话与开发对话协作

关联需求：REQ-20260908-008。建立日期：2026-09-08。

## 分工

用户继续在原对话提交需求、截图、缺陷和验收反馈，不必在两个对话之间复制信息。原对话是协调入口，开发对话是同一项目下的长期执行入口；这是两个可互相发消息的 Codex 对话，不依赖仅存于单轮的临时子代理。

协调入口负责：先更新[唯一需求台账](../requirements-backlog.md)，分析需求、给出建议、确定优先级和验收口径，将任务与记录位置交给开发对话，阅读并转述其回传，再向用户汇报或请求必要决定。不执行产品开发、测试、构建、代码审查、合并或发布收尾，也不重复开发入口的验证工作。

开发入口负责：读取项目规则、台账、当前状态与指定规格，在隔离工作区实现、测试、自审/独立审查和补文档，并负责需求记录提交、获授权的主分支整合及全部收尾，再回传代码与验证证据。不自动扩大范围、消费凭证/重置券或发布。

## 派工与回传

1. 协调入口先检查开发对话是否已有工作。新想法只登记；除非用户改变优先级，不打断当前工作。
2. 派工包含需求 ID、目标、限制、验收口径、需求/规格提交 SHA、主仓库路径和协调对话的回传 ID。主工作区 `.agent-coordination.local.json` 保存本机绑定并被 Git 忽略；ID 只用于本机绑定和工具消息，不写入公开产品文档。每次派工先核对绑定指向的实际对话状态。
3. 开发对话先核对自己的 checkout 是否包含派工基线。若为旧分支，先检查工作树与提交状态，再安全引入已提交需求；禁止覆盖其他改动或强制重置。工作区不共享未提交文件，不能假设另一窗口修改立即可见。
4. 开发过程中用同一台账记录当前事项与证据。在不同 checkout 修改台账时，只更新自己负责的行/记录；由开发入口整合提交，保留协调入口期间新增的需求，不能用旧文件整份覆盖。未提交需求的交接应明确文件和归属；涉及主工作区的进行中合并，先接管该状态再继续，不覆盖或丢弃现有改动。
5. 完成、阻塞或需要用户选择时，开发对话主动向派工指定的协调对话发送结果消息。消息注明“开发结果回传”、需求 ID、提交/分支/工作区、测试、限制、需用户确认内容和是否发布；无需用户切换窗口。
6. 协调入口收到回传后阅读摘要、列出结果与未完成项；缺少证据时交回开发入口补充，不亲自执行测试、审查或合并。向用户明确区分开发报告的实现、测试、合并、发布、真机验收状态，不凭“完成”二字推断全部完成。
7. 可执行需求结束后开发对话结束当前轮并待命，不空转轮询。下一次由协调入口发送新任务唤起；若回传未到，协调入口使用任务状态查询/等待核对，不虚构后台监控已运行。
